= Module 7: SRE Copilot Capstone
:navtitle: SRE Copilot Capstone

The capstone extension runs a three-agent observability fleet — three
specialist agents, each with its own narrow permission — against the
deployed Secure Agent Workspace. Participants verify the governance-signed
network ceiling live, watch the East-West wall hold, drive a real outage
in the browser, and confirm the remediation as a human.

Prerequisites: SAW up and Module 4's client configuration only — the
raw OpenShell modules (1-2) are not a prerequisite, so time-constrained
participants can jump straight here.

== Why this matters

Enterprises do not stall on whether AI agents *can* help operate systems —
they stall on "what can this agent see, what can it do, and who is
accountable when it is wrong?" In regulated environments, agent access has
to be a reviewed contract: least-privilege, per-role, auditable, revocable,
deployed as code. The three-agent fleet is that pattern in miniature.

[cols="1,2,2",options="header"]
|===
| Agent | Business job | What breaks without the policy

| `metrics`
| *On-call copilot / incident triage.* A first responder asks
plain-language questions and gets quantified answers from live telemetry —
without dashboard admin or any write path.
| An agent with blanket cluster read is an unmonitored copy of your most
sensitive dashboards — one prompt injection away from exfiltration.

| `traces`
| *Agent forensics + self-diagnostics.* Someone must be able to answer
"what did the agent *actually* do?" — for debugging, for audit, for the
transparency regulators increasingly demand.
| No evidence trail means "the agent did it" is unfalsifiable — you can
neither debug it nor defend it to an auditor.

| `analyst`
| *Zero-exfiltration reporting.* An objective synthesizer that is *unable*
to reach any telemetry by construction. The leak risk is designed out, not
trusted away.
| A summarizing agent with full read access is a natural exfiltration
channel — it touches everything and repeats everything.
|===

*The one-line takeaway:* specialists with narrow mandates, an analyst with
none, humans confirming every action — access as a reviewed contract is
what makes AI agents deployable in an enterprise.

== How governance holds this together

The *governance interceptor* is the platform's policy gatekeeper. It sits
between the gateway and every sandbox creation: it *signs* each sandbox's
policy, *vends* the provider profiles agents may use, and *rejects* any
operation that falls outside the governance baseline — fail-closed.

For this module the interceptor vends the fleet's *network ceiling*: the
signed policy the sandbox runtime actually enforces. On this release
(0.1.2-rhaiv.0) every fleet sandbox — however scoped its `--policy` at
create — is enforced against the same interceptor-signed ceiling, and that
ceiling draws two lines that are verified live below:

* *East-West protection:* in-cluster service addresses are absent from the
  ceiling, so a fleet sandbox cannot reach *any* internal service — not the
  telemetry proxy, not a database, not a neighboring pod. An agent sandbox
  cannot wander the cluster's internal network.
* *Ceiling allowlisting:* the one external endpoint the ceiling names is
  the approved model gateway (`build.nvidia.com`). If the endpoint is not
  on the ceiling's guest list, the connection is refused before HTTP.

The signed ceiling is what the sandbox runtime enforces — so the "guest
list" is not an agent's promise, it is governance-enforced fact. Every
claim in this module is verified from outside the agent by paired probes
and audit evidence, never taken from the agent's own output.

== The fleet design

[cols="1,2,2",options="header"]
|===
| Agent | Allowed backend | Job

| `metrics`
| Prometheus (the cluster metrics store, queried through Thanos) via the telemetry proxy
| Quantify rates, saturation, and failing workloads from live cluster metrics.

| `traces`
| MLflow (Red Hat OpenShift AI) via the telemetry proxy
| Read and reason over AI agent execution traces — agents auditing agents.

| `analyst`
| None — zero egress
| Combine findings and recommend a root cause and fix, without any way to
verify them itself.
|===

The backends sit behind a plain-HTTP telemetry proxy (the sandbox egress
proxy inspects HTTP; TLS-only upstreams route through it). The fleet
design originates in the `nemoclaw-openshift-launchable` sample (Scout,
Gauge, Trace, Probe, Sage), scaled to three agents for this environment.

On this release the interceptor enforces the shared ceiling on every fleet
sandbox — the guest lists above are the *reviewed intent*, shipped as
policy manifests in git, and the paired probes below prove what the
runtime actually enforces. The good news is on the wall side: no fleet
sandbox can reach any in-cluster service, whichever specialist it is.

== Extension prerequisites

The capstone environment is **Argo-managed from this repository**: the
workshop GitOps chart (`{gitops_root}/`) brings the demo shop, the MLflow
instance, the telemetry proxy, the incident console, and the planted
incident data up as the `module-7-prereqs` child in the cluster's
`{gitops_namespace}` instance. On GitOps-provisioned clusters (RHDP orders)
the order's chart deploys it; otherwise the facilitator applies it once —
before or after the SAW deployment, since the child holds in retry until SAW
(module 6) and the MLflow operator are healthy:

[source,bash,role="execute",subs="attributes+"]
----
make -C automation capstone-bootstrap
oc get application module-7-prereqs -n {gitops_namespace}   # Synced, then Healthy
----

NOTE: The DataScienceCluster that deploys RHOAI's components (the MLflow
operator among them) is GitOps-managed here too:
`{gitops_root}/capstone/dsc.yaml`, synced as part of `module-7-prereqs`. To customize
your RHOAI deployment — enable or remove components — edit the
`managementState` entries in that file (`Managed` deploys the component,
`Removed` tears it down), commit and push, and Argo's self-heal reconciles
the change on the cluster. Check what is enabled with `oc get
datasciencecluster default-dsc -o yaml`. Do not create or edit the
DataScienceCluster directly on the cluster: Argo reverts manual changes.

NOTE: *If the fleet script failed on a cluster and participants hit missing
prerequisites* (sandboxes never Ready, Module 7 exec commands failing), the
diagnostic is one object: `oc get application module-7-prereqs -n
{gitops_namespace}` — stuck OutOfSync/retrying means the SAW pattern never
installed. The remedy is one idempotent command — the workshop side
(DSC, MLflow, proxy, console, traces) recovers itself the moment SAW is
healthy:

[source,bash,role="execute",subs="attributes+"]
----
./fleet-install.sh --only <cluster-name>
----

That bootstraps the single cluster and blocks until `module-7-prereqs` is
Synced/Healthy. Before participants arrive, run `./fleet-status.sh --gate`
across the fleet: it exits non-zero if any cluster is not ready.

The PostSync seed job — it runs after every successful Argo CD sync — plants
the agent-session traces of a *prior* incident
(`INC-4127`) into MLflow — the data the traces agent investigates below —
and re-plants idempotently on each sync. What stays with you:

* the sandbox hand-off files the module's exec commands read:
  xref:attachment$plant-incident-traces.sh[plant-incident-traces.sh] run on
  the workspace VM stages `/tmp/incident-search.json`,
  `/tmp/mlflow.token` and `/tmp/agent-session-trace.json` inside the
  `traces` sandbox (idempotent — it also refreshes the planted story), and
  stages `/tmp/sa.token`, a read-only bearer token, in the `metrics`
  sandbox environment.

== Provision the fleet

The three fleet sandboxes are yours to create — the same way an enterprise
deploys a governance-scoped agent fleet: policies reviewed in git, applied at
sandbox create. The three policy manifests ship with this workshop's
automation (`{automation_repo}/policies/sandbox-policy-fleet-*.yaml`), and
the governance interceptor signs each policy at create time — it only signs
network access it governs, so a policy naming an undeclared backend fails
closed.

NOTE: On this release (0.1.2-rhaiv.0) the per-sandbox `--policy` narrowing
is accepted at create but not reflected in enforcement — every fleet
sandbox is enforced against the same interceptor-signed ceiling (a
documented known limitation). The manifests above remain the reviewed
intent, and Exercise 1 shows you how to read the effective policy either
way.

From your workstation, with the gateway selected and logged in (module 4):

[source,bash,role="execute",subs="attributes+"]
----
for agent in metrics traces analyst; do
  openshell --gateway {saw_gateway_name} sandbox create --name "$agent" \
    --from quay.io/rh-ai-quickstart/openclaw-openshell@sha256:69b2701ec9bb61194d901e51554c205d0ea7f09c04301e41923c468f082bb6c8 \
    --policy "{automation_repo}/policies/sandbox-policy-fleet-$agent.yaml" \
    --no-tty --detach -- sh -c 'sleep 86400'
done
openshell --gateway {saw_gateway_name} sandbox list
----

Pass condition: three sandboxes (`metrics`, `traces`, `analyst`) report
Ready. The fleet agents are CLI-driven and attach no inference provider —
the analyst's zero egress depends on it. Pin the image the same way the BOM
does: the `openclaw-openshell` base the workshop mirrors (the
`nemoclaw-sandbox` image lacks a usable PATH for the OpenClaw shebang, so
CLI-created sandboxes must use `openclaw-openshell`).

The fleet sandboxes live in the gateway's default workspace, so the exec
commands below omit `--workspace`. If you create them in `{saw_workspace}`,
add `--workspace {saw_workspace}` to each command and set
`WORKSPACE={saw_workspace}` for the GUI tunnel in Exercise 3.

The telemetry reads in Exercise 3 run from the operator side — your VM,
through a port-forward — because the East-West wall denies in-cluster
egress from fleet sandboxes (that denial is the good story, and Exercise 2
proves it). Start the port-forward once and keep it running; every MLflow
request needs it:

[source,bash,role="execute",subs="attributes+"]
----
oc -n openshell-agents port-forward svc/telemetry-proxy 8081:8081 >/dev/null 2>&1 &
----

Pull the sandbox hand-off files the plant-incident-traces.sh job staged
(the `traces` sandbox holds them) into your VM shell, and resolve the
MLflow experiment id once — every MLflow request needs it:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {saw_gateway_name} sandbox exec -n traces -- cat /tmp/mlflow.token > /tmp/mlflow.token
export MLFLOW_EXPERIMENT_ID=$(curl -s --max-time 15 \
  -H "Authorization: Bearer $(cat /tmp/mlflow.token)" \
  -H "X-MLFLOW-WORKSPACE: openshell" \
  "http://127.0.0.1:8081/mlflow/api/2.0/mlflow/experiments/get-by-name?experiment_name=sre-copilot-fleet" \
  | jq -r .experiment.experiment_id)
echo "experiment id: $MLFLOW_EXPERIMENT_ID"
----

== Exercise 1: Verify the fleet and its guest lists

All three sandboxes are Ready, and each one carries the *interceptor-signed
ceiling policy* — the same signed baseline lands on every fleet sandbox:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {saw_gateway_name} sandbox list
openshell --gateway {saw_gateway_name} policy get metrics --full
openshell --gateway {saw_gateway_name} policy get analyst --full
openshell --gateway {saw_gateway_name} policy get traces --full
----

Pass condition: three sandboxes report Ready, and each `policy get --full`
returns the governance-signed ceiling — same signature on all three, the
interceptor's contract with every sandbox it vends. The per-agent guest
lists in the git manifests are the reviewed intent; on this release
enforcement reflects the common ceiling (see the note in "Provision the
fleet"). What matters for security — and what Exercise 2 proves — is that
the ceiling itself is signed, enforced, and deny-by-default.

== Exercise 2: Prove the walls with paired probes

This is the money exercise: two paired probes, one from inside a fleet
sandbox and one control from outside, that show the East-West wall holding.
The sandbox image ships Node (`/usr/bin/node`), so the probes use Node's
`fetch` — and a denial arrives as `EACCES` before any HTTP status.

*Probe 1 — the declared in-cluster backend, from the sandbox (East-West
test).* The `metrics` sandbox names the telemetry proxy as its backend, and
the wall refuses it anyway — in-cluster service addresses are not on the
ceiling's guest list:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {saw_gateway_name} sandbox exec -n metrics -- \
  /usr/bin/node -e 'fetch("http://telemetry-proxy.openshell-agents.svc.cluster.local:8080/api/v1/query?query=up").then(r=>console.log("HTTP",r.status)).catch(e=>console.log("DENIED:",(e.cause&&e.cause.code)||e.message))'
----

*Control — the same endpoint from your VM.* The service is up and
reachable from the operator side; only the sandbox is walled off:

[source,bash,role="execute",subs="attributes+"]
----
oc -n openshell-agents port-forward svc/telemetry-proxy 18080:8080 >/dev/null 2>&1 &
curl -s -o /dev/null -w 'HTTP %{http_code}\n' --max-time 15 \
  "http://127.0.0.1:18080/api/v1/query?query=up"
----

*Probe 2 — the ceiling's allowlisted model endpoint, from the sandbox.*
The one external host the ceiling names is the approved model gateway, and
it is reachable — proving the denial above is policy, not a broken network:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {saw_gateway_name} sandbox exec -n metrics -- \
  /usr/bin/node -e 'fetch("https://build.nvidia.com").then(r=>console.log("HTTP",r.status)).catch(e=>console.log("DENIED:",(e.cause&&e.cause.code)||e.message))'
----

Pass condition: the in-cluster probe from the sandbox fails with `EACCES`
(denied before any HTTP), the VM control returns an HTTP status — 401
without a bearer token is fine, it proves the path works — and the
allowlisted `build.nvidia.com` probe returns HTTP 200 from the sandbox.
That trio *is* the security story, demonstrated live: an agent sandbox
cannot wander the cluster's internal network, while the one approved
external endpoint works.

Repeat probe 1 from the `analyst` and `traces` sandboxes: identical
`EACCES`. The ceiling is signed onto every fleet sandbox — the wall does
not depend on which specialist the agent is, and it cannot be widened by
the agent.

== Exercise 3: Read live telemetry through the operator plane

The wall you proved in Exercise 2 is the good news: fleet sandboxes cannot
reach in-cluster services, the telemetry proxy included. So the telemetry
evidence is read from the *operator side* — your VM, through the
port-forward you started — while the agent plane stays fully isolated.
The proxy answers 401 without a bearer token — the authentication
requirement is itself evidence that the path works. With the
facilitator-vended read-only service account token, you query real
cluster metrics.

Open the agent surfaces alongside your evidence queries. The fleet sandboxes
live on `{saw_gateway_name}`, so both agent surfaces from earlier modules
reach them:

* *Control UI (browser)* — the dashboard Route forwards only `{saw_sandbox}`;
  the fleet sandboxes use the shipped tunnel, as in Module 5. From
  the SAW checkout root:

[source,bash,role="execute",subs="attributes+"]
----
SANDBOX_NAME=metrics GATEWAY_NAME={saw_gateway_name} \
  ./scripts/openshell-saw-gui.sh
----

Open the printed URL and chat with the `metrics` agent while watching tool
activity live. Asking the agent to reach telemetry and watching the wall
refuse it is a live isolation demo, not a failure.

* *OpenShell TUI (operator view)* — in a second terminal, as in Module 2:

[source,bash,role="execute",subs="attributes+"]
----
openshell term --gateway {saw_gateway_name}
----

Keep the evidence queries below in the first terminal: user-level interaction
and operator management side by side.

Pull the read-only service account token out of the `metrics` sandbox and
query the live cluster metrics from your VM — the operator side of the
wall:

[source,bash,role="execute",subs="attributes+"]
----
oc -n openshell-agents port-forward svc/telemetry-proxy 18080:8080 >/dev/null 2>&1 &
openshell --gateway {saw_gateway_name} sandbox exec -n metrics -- cat /tmp/sa.token > /tmp/sa.token
curl -s --max-time 15 -H "Authorization: Bearer $(cat /tmp/sa.token)" \
  "http://127.0.0.1:18080/api/v1/query?query=kube_deployment_status_replicas_available%7Bnamespace%3D%22demo%22%7D"
----

The `traces` story reads AI agent execution traces from MLflow. The
facilitator planted the agent-session traces of the prior incident — the
record of what the fleet *actually did* the last time this incident ran.
Search by incident, not by trace ID, is the natural read pattern. Pull the
staged search payload out of the `traces` sandbox and run the identical
search the agent story uses:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {saw_gateway_name} sandbox exec -n traces -- cat /tmp/incident-search.json > /tmp/incident-search.json
curl -s --max-time 15 -X POST \
  -H "Authorization: Bearer $(cat /tmp/mlflow.token)" \
  -H "X-MLFLOW-WORKSPACE: openshell" \
  -H "Content-Type: application/json" \
  --data-binary @/tmp/incident-search.json \
  "http://127.0.0.1:8081/mlflow/api/3.0/mlflow/traces/search"
----

Pass condition: the search returns the planted incident session, ordered
by time — alert triage, the replica-collapse queries, the traces agent's
own audit of the fleet, the analyst synthesis, the human approval, and the
recovery check — each trace tagged with the role that ran it
(`agent.role`: `metrics`, `traces`, `analyst`, `ops`). Narrow the search
the same way for any question (for example
`tags."agent.role" = "metrics"`), then drill into one finding by ID.
Traces ingested through OTLP (OpenTelemetry's trace protocol) carry a `tr-`
prefix on their trace ID:

[source,bash,role="execute",subs="attributes+"]
----
# TRACE_ID: copy one from the search result above
TRACE_ID=tr-26e481fb6b1c17d11918ba6b3d1445ad
curl -s --max-time 15 \
  -H "Authorization: Bearer $(cat /tmp/mlflow.token)" \
  -H "X-MLFLOW-WORKSPACE: openshell" \
  "http://127.0.0.1:8081/mlflow/api/3.0/mlflow/traces/$TRACE_ID?experiment_id=$MLFLOW_EXPERIMENT_ID"
----

This is *agents auditing agents*: the trace store is a record of agent
behavior — which tools ran, what was sent, who approved what — that the
governed agent story can be interrogated against. The workspace header is
mandatory on every MLflow request: without it the proxy rejects the call
outright.

Finally, watch a trace arrive live. The staged sample is a complete agent
session; pull it out of the `traces` sandbox and ingest it through the
OpenTelemetry endpoint — the write path the fleet story uses — noting that
the acknowledgement is empty: OTLP carries no response body, which is
exactly why search, not IDs, is how you find what you just wrote. Then
re-run the incident search above and see your own session appear in the
results:

[source,bash,role="execute",subs="attributes+"]
----
# Ingest your own session trace (the write path the fleet story uses live):
openshell --gateway {saw_gateway_name} sandbox exec -n traces -- cat /tmp/agent-session-trace.json > /tmp/agent-session-trace.json
curl -s --max-time 15 -X POST \
  -H "x-mlflow-experiment-id: $MLFLOW_EXPERIMENT_ID" \
  -H "X-MLFLOW-WORKSPACE: openshell" \
  -H "Authorization: Bearer $(cat /tmp/mlflow.token)" \
  -H "Content-Type: application/json" \
  --data-binary @/tmp/agent-session-trace.json \
  "http://127.0.0.1:8081/v1/traces"

# Re-run the incident search — your session (session.demo: participant)
# now appears in the results alongside the planted fleet traces.
curl -s --max-time 15 -X POST \
  -H "Authorization: Bearer $(cat /tmp/mlflow.token)" \
  -H "X-MLFLOW-WORKSPACE: openshell" \
  -H "Content-Type: application/json" \
  --data-binary @/tmp/incident-search.json \
  "http://127.0.0.1:8081/mlflow/api/3.0/mlflow/traces/search"
----

GUI view: the MLflow instance also serves a tracking UI. Check whether the
environment exposes a Route for it:

[source,bash,role="execute",subs="attributes+"]
----
oc -n redhat-ods-applications get route
----

If an MLflow Route is listed, open it and find the `sre-copilot-fleet`
experiment: the planted `INC-4127` session appears as a visual trace
waterfall — each span (one step in the trace: a tool call the fleet made),
tagged with the role that
ran it. Seeing the same evidence as a picture next to the CLI output is the
"agents auditing agents" demo moment. If no Route is exposed, the CLI trace
reads above are the same evidence.

== Exercise 4: The incident loop

Open the incident console and drive a real outage, with the fleet
investigating. The console deploys to the `{saw_namespace}` namespace — get
its URL first:

[source,bash,role="execute",subs="attributes+"]
----
oc -n {saw_namespace} get route incident-console
----

. Record the healthy baseline: the `demo/shop` deployment reports two
  ready replicas.
. *Inject the outage* — scale the shop to zero from the console. Human
  action, not the agent's.
. Run the fleet investigation: the `metrics` story finds the
  available-replica collapse with the Exercise 3 query (re-run it from the
  VM — the East-West wall keeps the sandboxes off the internal network, so
  the operator plane feeds the specialists their evidence); the `traces`
  story audits what the fleet did last time by searching the planted
  `INC-4127` session; the `analyst` combines the findings. Note what the
  analyst *cannot* do — it has no way to verify anything itself, by design.
. *Confirm the remediation* — restore the shop from the console after
  reviewing the recommendation.
. Verify recovery: the shop returns to two ready replicas.

The agents recommend; they never receive Kubernetes write access — and the
Exercise 2 probes prove they never receive in-cluster network access
either. The console's confirmation button is *not* durable, identity-bound
approval evidence — a production workflow needs an authenticated approval
record and a controlled delivery path such as a reviewed Git change
reconciled by Argo CD.
