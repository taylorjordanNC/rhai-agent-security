= Module 1: Deploy and Operate Basic OpenShell
:navtitle: Basic OpenShell

In this module you install the Agent Sandbox controller and OpenShell gateway
on OpenShift, register the gateway with the CLI, create the raw sandbox used by
the policy exercises, and deploy OpenClaw on the raw pod boundary.

*Estimated time:* 30 minutes

== Technical context

The Helm release creates the gateway and sandbox substrate; it does not deploy
an agent application. Distinguish the Kubernetes resources that host the
service from the OpenShell resources that govern an individual sandbox.

== Learning objectives

* Deploy the harness OpenShell Helm chart on OpenShift.
* Explain the Agent Sandbox controller, namespace, SCC admission, Helm release,
  and gateway storage used by the harness baseline.
* Register the gateway and verify the CLI connection.
* Create and inspect a disposable sandbox.
* Deploy OpenClaw on the raw gateway and identify the runtime boundary.

== Exercise 1: Deploy the gateway

Use the bundled harness automation for the participant baseline. It is
intentionally a plaintext, unauthenticated evaluation path; the SAW deployment
module adds OIDC, TLS, VM isolation, and centralized secrets.

Run this module from the `rhai-agent-security` repository root:

[source,bash,role="execute",subs="attributes+"]
----
make -C {automation_repo} install-openshell \
  OPENSHELL_VERSION={openshell_version}
----

image::01-openshell-deploy-success.png[OpenShell deploy success,link=self,window=blank,width=700]

The harness installation sequence is:

. Installs the Red Hat Agent Sandbox operator through OLM, which provides the
  Kubernetes `Sandbox` CRDs and controller.
. Creates the `openshell` namespace.
. Grants the privileged SCC required by this older evaluation baseline.
. Creates the gateway JWT signing Secret.
. Installs the NVIDIA OpenShell Helm chart with the harness OpenShift settings.
. Pins the default sandbox image to `{openshell_sandbox_image}`.
. Waits for the gateway StatefulSet and its PVC.
. Deploys the in-cluster `http-echo` service used by the Module 2 policy exercises.
. Leaves the unauthenticated gateway internal to the cluster. The CLI reaches it
  only through a local port-forward.

The privileged SCC is a limitation of this harness baseline, not a production
recommendation. SAW provides the stronger per-user VM boundary used later.

Start a local gateway port-forward after the script completes. Keep the
background process running through Module 2:

[source,bash,role="execute",subs="attributes+"]
----
oc -n {openshell_namespace} port-forward svc/openshell 8080:8080 \
  >"$HOME/openshell-port-forward.log" 2>&1 &
echo $! >"$HOME/openshell-port-forward.pid"
sleep 2
----

[source,bash,role="execute",subs="attributes+"]
----
openshell gateway remove {raw_gateway_name} 2>/dev/null || true
openshell gateway add "http://127.0.0.1:8080" --local --name {raw_gateway_name}
openshell gateway select {raw_gateway_name}
openshell status
----

image::02-openshell-gateway-success.png[OpenShell gateway success,link=self,window=blank,width=700]

The Agent Sandbox controller reconciles the sandbox request, while OpenShell
provides the gateway and supervisor that enforce the runtime boundary. The
harness installs the Red Hat Agent Sandbox operator through OLM using channel
`{agent_sandbox_channel}`.

This is a plaintext evaluation path bound to the local workstation. Do not
create an external Route for it. The SAW gateway uses OIDC and TLS on a
workspace VM instead of reusing this unauthenticated gateway.

[source,bash,role="execute",subs="attributes+"]
----
oc -n {openshell_namespace} rollout status statefulset/openshell
----

== Exercise 2: Verify the deployment

Check the resources the chart created:

[source,bash,role="execute",subs="attributes+"]
----
oc -n {openshell_namespace} get statefulset,pods,svc,pvc
oc get crd sandboxes.agents.x-k8s.io
----

image::03-openshell-verify.png[OpenShell verify success,link=self,window=blank,width=700]

The gateway pod should be `Running`, the PVC should be `Bound`, and the Agent
Sandbox API should exist. If the gateway is pending, inspect the PVC,
StorageClass, pod events, and StatefulSet status. The privileged SCC applies to
sandbox pods, not the gateway pod.

These checks establish that the control plane is healthy, state has durable
storage, and the cluster accepted the sandbox API.

== Exercise 3: Create the test sandbox

Create the raw policy-test sandbox. This is intentionally managed with
OpenShell, not NemoClaw:

[source,bash,role="execute",subs="attributes+"]
----
openshell sandbox create --name {raw_sandbox_name} --no-auto-providers --no-tty -- true
----

image::04-openshell-create-test-sandbox.png[OpenShell create test sandbox success,link=self,window=blank,width=700]

[source,bash,role="execute",subs="attributes+"]
----
openshell sandbox list
openshell sandbox get {raw_sandbox_name}
oc -n {openshell_namespace} get pods -o wide
----

The gateway is the control plane, the `Sandbox` resource is the Kubernetes
request, and `{raw_sandbox_name}` is the reconciled sandbox. The sandbox remains running for
the next module.

The raw `{raw_sandbox_name}` sandbox is deliberately agent-neutral. It provides a controlled
baseline before NemoClaw adds OpenClaw configuration, inference, lifecycle, and
dashboard behavior.

== Exercise 4: Diagnose and recover gateway connectivity

Stop only the port-forward process created earlier, verify the expected failure,
and restore it:

[source,bash,role="execute",subs="attributes+"]
----
PID=$(cat "$HOME/openshell-port-forward.pid")
ps -p "$PID" -o command= | grep -Eq 'oc .+port-forward .+svc/openshell'
kill "$PID"
sleep 2

ENDPOINT_UNREACHABLE=false
if openshell --gateway {raw_gateway_name} status >/dev/null 2>&1; then
  echo 'ERROR: gateway remained reachable after stopping the port-forward'
else
  ENDPOINT_UNREACHABLE=true
  echo 'EXPECTED: local gateway endpoint is unavailable'
fi

oc -n {openshell_namespace} port-forward svc/openshell 8080:8080 \
  >"$HOME/openshell-port-forward.log" 2>&1 &
echo $! >"$HOME/openshell-port-forward.pid"
sleep 2
openshell --gateway {raw_gateway_name} status
test "$ENDPOINT_UNREACHABLE" = true
----

If recovery fails, inspect `$HOME/openshell-port-forward.log`, the Service
endpoints, and gateway pod readiness before changing the gateway registration.

== Exercise 5: Deploy OpenClaw with OpenShell

So far the raw track has used agent-neutral sandboxes. Deploy the OpenClaw
runtime on the same raw gateway to see the agent boundary before Secure Agent
Workspace adds the VM:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {raw_gateway_name} sandbox delete {raw_openclaw_name} 2>/dev/null || true
openshell --gateway {raw_gateway_name} sandbox create \
  --name {raw_openclaw_name} --no-auto-providers \
  --from {raw_openclaw_image} --no-tty -- true
----

[source,bash,role="execute",subs="attributes+"]
----
OPENCLAW_READY=false
for i in $(seq 1 30); do
  if openshell --gateway {raw_gateway_name} sandbox exec \
    -n {raw_openclaw_name} -- true >/dev/null 2>&1; then
    OPENCLAW_READY=true
    break
  fi
  sleep 5
done
test "$OPENCLAW_READY" = true

openshell --gateway {raw_gateway_name} sandbox exec \
  -n {raw_openclaw_name} -- openclaw --version
----

image::05-openshell-deploy-openclaw.png[OpenShell deploy OpenClaw success,link=self,window=blank,width=700]

Pass condition: the sandbox is `Ready` and `openclaw --version` reports the
agent runtime inside the pod. Connect interactively with
`openshell sandbox connect {raw_openclaw_name}` to see the agent runtime, then
exit with `exit`.

The raw gateway holds no inference provider, so this exercise proves the
deployment boundary only: OpenClaw runs inside an OpenShell sandbox created and
governed by the raw gateway. Model-backed execution arrives in Module 4, where
the SAW gateway holds the provider and the NemoClaw runtime manages the agent
lifecycle. The image is pinned to `{raw_openclaw_image}` for the same reason as
the base sandbox image.

== Evidence checkpoint

Before continuing, verify that you can identify:

* Which cluster-scoped dependency must exist before the Helm chart can create
  sandboxes?
* Which SCC the harness uses and which workload receives it.
* Where is the gateway's SQLite state stored?
* Which operations are performed by the OpenShell CLI rather than raw `oc`?
* Where does OpenClaw run in this module, and what does it still lack?

.Answer key
[%collapsible]
====
* The Agent Sandbox controller (the `sandboxes.agents.x-k8s.io` `Sandbox` CRD,
  installed by the Red Hat Agent Sandbox operator) must exist before the Helm
  chart can create sandboxes.
* The harness grants the `privileged` SCC to the `openshell-sandbox`
  ServiceAccount; sandbox pods receive it, the gateway pod does not.
* Gateway state is stored in the 1Gi `openshell-data-openshell-0` PVC mounted by
  the `openshell` StatefulSet (its SQLite database).
* Gateway registration (`gateway add`, `gateway select`) and the sandbox
  lifecycle (`sandbox create`, `sandbox get`, `sandbox exec`, `sandbox delete`)
  run through the OpenShell CLI. Raw `oc` manages cluster resources and the
  port-forward only.
* OpenClaw runs inside the `{raw_openclaw_name}` sandbox on the raw pod
  boundary. It has a runtime but no inference provider; model-backed execution
  arrives in Module 4 behind the SAW gateway.
====
