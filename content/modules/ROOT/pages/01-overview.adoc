= Architecture and Control Boundaries
:navtitle: Architecture and Control Boundaries

== Control questions

An agent that can read files, call APIs, install packages, or change systems
has a larger blast radius than a chat application. These are the same four
questions customers ask before allowing agents on their platform, and a
recommendation has to answer each one with evidence rather than assertion. The
workshop evaluates:

* *Where does the agent run?*
* *What can it reach?*
* *Where are credentials held?*
* *How can the operations team prove what happened?*

== The stack

[cols="1,2,3",options="header"]
|===
| Layer | Component | Responsibility

| Platform
| One multinode OpenShift {ocp_version} cluster
| The harness provides the evaluation path on plain pods (the raw track).
  Secure Agent Workspace
  provides the cluster-resident NemoClaw/OpenClaw path inside a per-user VM.

| Sandbox control plane
| NVIDIA OpenShell
| A gateway and supervisor model for creating, governing, observing, and
  connecting to agent sandboxes.

| Agent runtime
| OpenClaw managed by the SAW NemoClaw runtime
| The agent process, tools, workspace, and browser-facing control UI run inside
  the per-user VM. OpenShell contains the sandbox inside that VM.

| Inference
| OpenShell privacy router
| The managed agent calls the virtual `inference.local` endpoint. The gateway
  holds the upstream provider configuration and credential.

| Production workspace
| Secure Agent Workspace
| The workshop SAW implementation provisions a dedicated KubeVirt VM for the
  configured owner, with OpenShell and the agent inside it, plus OIDC,
  Vault/External Secrets, a governance interceptor, and GitOps-managed policy.
|===

== Two gateways, one important distinction

Two components to understand and be able to explain are:

* The *OpenShell gateway* is the platform control plane. The raw track — the
  workshop's name for the evaluation path on plain pods, no VM layer — reaches
  the harness gateway through a local port-forward; the SAW track reaches a
  per-user gateway VM through an OIDC-authenticated Route.
* The *OpenClaw gateway* is the agent's own control UI and WebSocket service,
  running inside the managed sandbox. The SAW BOM and setup Job configure its
  lifecycle, and the fork's Make targets provide local dashboard forwarding.

The command `openshell sandbox exec` crosses the OpenShell boundary. The
command `openclaw` operates the agent once you are inside that boundary. Two
live surfaces make the distinction visible: Module 2 runs the OpenShell TUI in
a second terminal, and Module 5 drives the browser Control UI alongside CLI
evidence.

== Workshop progression

=== 1. Capability

Create a disposable sandbox and inspect both the OpenShell and Kubernetes
resources that represent it.

=== 2. Containment

Inspect the effective policy, run allowed and denied operations, and correlate
each result with gateway evidence. The raw-track harness is an evaluation
boundary, not the SAW VM-isolated deployment.

=== 3. Usefulness

Use a deployed SAW NemoClaw sandbox, verify OIDC and workspace scope, and run
OpenClaw in its permitted workspace. The standalone `nemoclaw onboard` workflow
is not a remote OpenShift management command.

=== 4. Layered controls

Inspect the SAW VM, Keycloak OIDC configuration, Vault-backed secrets,
governance profiles, and Argo CD ownership. The VM adds a stronger runtime
boundary; it does not replace OpenShell policy.

=== 5. Operations

The optional fleet extension assigns telemetry capabilities to separate
sandboxes and requires confirmation before the incident workflow changes
cluster state.

== Interpretation guardrails

OpenShell enforces the declared sandbox policy at the supervisor, proxy, and
kernel boundary when the corresponding runtime control is active. It does not
guarantee that a model produces correct requests. Verify policy, runtime events,
and the observed result before making an enforcement claim.

Pod and VM isolation are layered deployment choices. The pod-based path exposes
the OpenShell controls directly. The SAW path places the gateway and agent inside a
dedicated VM for the configured owner and adds identity, secret delivery, and
GitOps-managed configuration.
